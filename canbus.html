CAN Bus Fleet Tracker

A Bluetooth odometer logger for buses, built with a Raspberry Pi Pico 2 W

Overview

Most fleet management systems need mileage for fueling, tax reports, maintenance schedules, etc. At my agency, this number is recorded manually. A driver reads the odometer out loud and someone writes it down. This is easy to get wrong and has caused service disruptions in the past.

This project is a small device that plugs into a bus's diagnostic port, reads the odometer from the J1939 network, and sends it over Bluetooth to a laptop. A Python script on the laptop saves each reading to an Excel file. The idea is that when a bus comes back to the bus barn after a shift, it connects to a Bluetooth receiver there and the odometer gets logged before the bus is shut off.

I based it on PiCCANTE, an open-source CAN bus tool for the Raspberry Pi Pico. I kept the hardware idea and wrote a much simpler program that only does one job. The CAN part uses can2040 through the ACAN2040 Arduino library.

Alert: Don't plug this into any transit vehicle without permission. It could interfere with the vehicle's systems, void warranties, or break agency policy, and you are responsible for any damage or safety issues. Try it on the bench first (see Testing).

J1939

The engine, transmission, brakes and dash on a bus all talk on a network called the CAN bus, which is two wires (CAN-High and CAN-Low) twisted together. Heavy vehicles use the J1939 protocol on top of it. Each message has a 29-bit ID, and part of that ID is the PGN, which says what's in the message. I use three of them:

PGNNameWhat's inside
65217High Resolution Vehicle DistanceTotal distance, 5 meters per step
65248Vehicle DistanceTotal distance, 0.125 km per step
65271Vehicle Electrical PowerBattery voltage, 0.05 V per step

The bus sends these on its own over and over. The logger doesn't have to ask for anything.

Most SN65HVD230 boards come with a 120 Ω resistor between CANH and CANL. The bus already has one at each end, so take it off before plugging into a real vehicle. Leave it on for bench testing.

can2040 acknowledges messages on the bus, so the Pico isn't completely passive. If you want it to only listen, wire the transceiver's CTX to 3V3 instead of GP5.

Code

The Pico program is C++ written in the Arduino IDE.

Bitrate

Most heavy vehicles run J1939 at 250,000 bits per second. Some newer ones use 500,000, so that's a setting at the top of the file.

#define J1939_BITRATE 250000      // some newer vehicles use 500000

can = new ACAN2040(CAN_PIO, CAN_TX_PIN, CAN_RX_PIN, J1939_BITRATE, F_CPU, canCallback);

Getting the PGN

The 29-bit ID holds the priority, the PGN, and the source address (which module sent it). For some message types (when the PF byte is under 240) the middle byte is a destination address instead of part of the PGN, so it gets masked off.

uint32_t j1939Pgn(uint32_t id) {
  uint32_t pf = (id >> 16) & 0xFF;
  uint32_t pgn = (id >> 8) & 0x3FFFF;   // EDP + DP + PF + PS
  if (pf < 240) {
    pgn &= 0x3FF00;                     // PDU1: drop destination address
  }
  return pgn;
}

Getting the odometer

J1939 sends numbers lowest byte first, so the code puts the four bytes back together. I keep the raw number as an integer and only turn it into kilometers when it's sent, so nothing gets rounded off. Anything 0xFB000000 or higher means "error" or "not available" and gets skipped.

bool hr = (pgn == PGN_HR_VEHICLE_DISTANCE);
uint32_t raw = hr ? le32(&msg->data[0]) : le32(&msg->data[4]);
if (raw > 0xFAFFFFFF) return;   // error / not available

If the bus sends both distance messages, the code uses the 5 meter one and ignores the 0.125 km one. Different modules can also send slightly different distances, so every reading includes the source address. ODO_SOURCE_ADDR can be set to only listen to one module.

Old readings

If the odometer hasn't come in for 5 seconds (usually the key is off), the logger sends an error instead of the last number it had.

Bluetooth

Once a minute, or whenever the laptop sends READ, the Pico sends one line: vehicle name, odometer in km, which message it came from, battery voltage, and source address.

ODO,BUS_01,80467.200,J1939-HR,27.60,00

ERR,BUS_01,NO_DATA    no odometer since power-up (key off? wrong bitrate? wiring?)
ERR,BUS_01,STALE      odometer stopped updating

Testing

I wrote a simulator that turns a second Pico into a fake bus. It sends PGNs 65217, 65248 and 65271 every second with an odometer that keeps counting up.

  1. Connect the two transceivers CANH to CANH, CANL to CANL, and GND to GND. Keep the 120 Ω resistor on both boards.
  2. Upload the simulator to the second Pico and open the Serial Monitor.
  3. Check that the logger's numbers match the simulator's.
  4. Press h to turn off the high resolution message. The logger should switch to J1939.
  5. Press p to pause. The logger should send STALE.

Instructions

Set up the Arduino IDE

  1. Add the board URL in File → Preferences:
    https://github.com/earlephilhower/arduino-pico/releases/download/global/package_rp2040_index.json
  2. In Boards Manager, install Raspberry Pi Pico/RP2040/RP2350.
  3. In Library Manager, install ACAN2040.
  4. Select Tools → Board → Raspberry Pi Pico 2 W.
  5. Select Tools → IP/Bluetooth Stack → IPv4 + Bluetooth.

Upload the logger

Open OdoLogger_J1939.ino, change VEHICLE_NAME for the bus, and upload. The Bluetooth name will be OdoLogger_ plus the vehicle name. If the Serial Monitor keeps showing NO_DATA, try 500000 for the bitrate.

Set up the laptop

pip install pyserial openpyxl

Pair with OdoLogger_BUS_01 in Bluetooth settings, then find the port:

  • Mac: /dev/cu.OdoLogger_BUS_01
  • Windows: the "Outgoing" COM port in Device Manager → Ports

Run it

Run odometer_to_excel.py with the port:

python odometer_to_excel.py /dev/cu.OdoLogger_BUS_01

To try it without any hardware, use test mode. It makes up readings.

python odometer_to_excel.py --test

Output

The script writes fleet_odometer_log.xlsx with two sheets:

SheetContents
LogDate, time, vehicle, odometer (km), odometer (miles), miles since last reading, source, battery voltage
TotalsFirst reading, last reading and total miles for each vehicle

Possible uses

If you have agency approval, you could do the following:

  • Plug it into a few buses and compare its readings to the dash and Cummins INSITE to make sure the numbers are right.
  • Leave a logger on each bus, powered from the diagnostic port instead of USB.
  • Switch to BLE so one receiver at the bus barn picks up every bus automatically when it pulls in, without pairing.
  • Read more from the bus, like active fault codes (DM1), engine hours and fuel used.
  • Send the readings straight into the fleet management system instead of an Excel file, so no one has to type in mileage.
