CAN Bus Fleet Tracker

A Bluetooth odometer logger for heavy vehicles, built with a Raspberry Pi Pico 2 W

Overview

Most fleet management systems need mileage for fueling, tax reports, maintenance schedules, etc. At my agency, this number is recorded manually. Someone writes the odometer down by hand after being read the number by a driver. This makes the process prone to human error and has resulted in service disruptions in the past. This project is a small device that plugs into a bus's diagnostic port, reads the odometer from the vehicle's J1939 network, and sends it over Bluetooth to a laptop. A Python script then saves each reading to an Excel file. When the bus returns to the bus barn after a shift, it will connect to the Bluetooth receiver in the area, which would then log the odometer before the bus is powered off.

It is based on PiCCANTE, an open-source CAN bus tool for the Raspberry Pi Pico. I kept the hardware idea and wrote a much simpler program that only does one job. CAN on the Pico is handled by can2040 through the ACAN2040 Arduino library.

Alert: It is not recommended to plug this into any transit vehicle without permission. Doing so could interfere with the vehicle's systems, void warranties, or break an agency policy, and you are responsible for any damage or safety issues that result. Test on the bench first (see Testing) and use the listen-only wiring.

J1939

Inside a heavy vehicle, the engine, transmission, brakes and dash all talk on a network called the CAN bus. It is CAN-High and CAN-Low twisted together. Heavy vehicles commonly use the J1939 protocol, which uses 29-bit extended CAN IDs. Every message has a number called a PGN that says what is inside it. The logger uses three:

PGNNameWhat's inside
65217High Resolution Vehicle DistanceTotal distance, 5 meters per step
65248Vehicle DistanceTotal distance, 0.125 km per step
65271Vehicle Electrical PowerBattery voltage, 0.05 V per step

Modules broadcast these messages on their own repeatedly, so the logger only has to listen.

Wiring

FromTo
Vehicle pin C (CAN-High)Transceiver CANH
Vehicle pin D (CAN-Low)Transceiver CANL
Pico GP5 (pin 7)Transceiver CTX (or 3V3 for listen-only, below)
Pico GP4 (pin 6)Transceiver CRX
Pico 3V3 OUT (pin 36)Transceiver 3V3
Vehicle pin A, Pico GND (pin 38)Transceiver GND
Remove the termination resistor. Most SN65HVD230 boards have a 120 Ω resistor between CANH and CANL. The vehicle's bus is already terminated at both ends, and a third resistor on the diagnostic port lowers the bus impedance and can cause errors. Remove it before connecting to a vehicle (keep it for bench testing).
Listen-only wiring. The can2040 library acknowledges messages, so by default the logger is an active node on the bus. Connecting the transceiver's CTX to 3V3 instead of GP5 keeps its driver off, so the logger can only listen.

Code

The Pico program is written in C++ with the Arduino IDE.

Listens at 250k

Most heavy vehicles run J1939 at 250,000 bits per second. Some newer ones use 500,000, which is a one-line change.

#define J1939_BITRATE 250000      // some newer vehicles use 500000

can = new ACAN2040(CAN_PIO, CAN_TX_PIN, CAN_RX_PIN, J1939_BITRATE, F_CPU, canCallback);

Decodes the PGN

A J1939 ID packs the priority, the PGN and the sender's source address into 29 bits. For some message types (PDU1, when the PF byte is under 240), the middle byte is a destination address and is not part of the PGN, so the code masks it out.

uint32_t j1939Pgn(uint32_t id) {
  uint32_t pf = (id >> 16) & 0xFF;
  uint32_t pgn = (id >> 8) & 0x3FFFF;   // EDP + DP + PF + PS
  if (pf < 240) {
    pgn &= 0x3FF00;                     // PDU1: drop destination address
  }
  return pgn;
}

Picks out the distance

J1939 sends numbers lowest byte first, so the code puts the four bytes back together. The raw count is kept as an integer and only converted to kilometers when it is sent, so no precision is lost on high-mileage vehicles. Values of 0xFB000000 and above mean "error" or "not available" and are skipped.

bool hr = (pgn == PGN_HR_VEHICLE_DISTANCE);
uint32_t raw = hr ? le32(&msg->data[0]) : le32(&msg->data[4]);
if (raw > 0xFAFFFFFF) return;   // error / not available

If a vehicle sends both distance messages, the 5-meter one is preferred and the 0.125 km one is only a fallback, so the reading never jumps between resolutions. Several modules can broadcast distance with slightly different values, so each reading includes the source address it came from, and ODO_SOURCE_ADDR can lock the logger to one module.

Knows when data is old

If the odometer hasn't been heard for 5 seconds (key off, bus asleep), the logger reports an error instead of repeating an old value. The CAN callback runs as an interrupt, so the main loop copies the shared data with interrupts briefly disabled.

Sends it over Bluetooth

Once a minute, or right away when the laptop sends READ, the Pico sends one line with the vehicle name, odometer in km, which PGN it came from, battery voltage and source address:

ODO,BUS_01,80467.200,J1939-HR,27.60,00

ERR,BUS_01,NO_DATA    no odometer since power-up (key off? wrong bitrate? wiring?)
ERR,BUS_01,STALE      odometer stopped updating

Testing

The J1939 simulator turns a second Pico and transceiver into a fake vehicle. It broadcasts PGNs 65217, 65248 and 65271 once a second with an odometer that keeps going up.

  1. Connect the two transceivers CANH to CANH, CANL to CANL, GND to GND. Keep the 120 Ω resistor on both boards (one at each end of the bench bus).
  2. Upload the simulator to the second Pico and open its Serial Monitor.
  3. Check that the logger's readings match the simulator's odometer.
  4. Press h to stop the high-resolution message (the logger should fall back to J1939) and p to pause (the logger should report STALE).

Instructions

Set up the Arduino IDE

  1. Add the board URL in File → Preferences:
    https://github.com/earlephilhower/arduino-pico/releases/download/global/package_rp2040_index.json
  2. In Boards Manager, install Raspberry Pi Pico/RP2040/RP2350.
  3. In Library Manager, install ACAN2040.
  4. Select Tools → Board → Raspberry Pi Pico 2 W.
  5. Select Tools → IP/Bluetooth Stack → IPv4 + Bluetooth.

Upload the logger

Open OdoLogger_J1939.ino, change VEHICLE_NAME for the bus, and upload. The Bluetooth name becomes OdoLogger_ plus the vehicle name. If the Serial Monitor shows NO_DATA and lots of parse errors, try a bitrate of 500000.

Set up the laptop

pip install pyserial openpyxl

Pair with OdoLogger_BUS_01 in Bluetooth settings, then find the port:

  • Mac: /dev/cu.OdoLogger_BUS_01
  • Windows: the "Outgoing" COM port in Device Manager → Ports

Run it

Give odometer_to_excel.py the port:

python odometer_to_excel.py /dev/cu.OdoLogger_BUS_01

To try it without any hardware, it can make up readings:

python odometer_to_excel.py --test

Output

The script writes fleet_odometer_log.xlsx with two sheets:

SheetContents
LogDate, time, vehicle, odometer (km), odometer (miles), miles since last reading, source, battery voltage
TotalsFirst reading, last reading and total miles for each vehicle

Readings where the bus did not move are skipped so the sheet stays short. Readings where the odometer goes backwards are rejected with a warning, since that means a wrong module, a bad message, or a logger moved to a different bus. The example below is made-up test-mode data.
