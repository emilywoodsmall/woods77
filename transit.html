Transit Schedule Adherence Analyzer

September 2026

Every run of a bus route repeats each day at the same scheduled times. This tool measures when the bus actually left each timepoint on every day, so the same scheduled leave time can be compared against many days of real departures, and runs that are consistently late stand out.

It works with any transit agency that publishes a standard GTFS schedule and GTFS-Realtime vehicle positions. Nothing in the code is specific to one agency. It was first tested on Butler County Regional Transit Authority (Ohio), where it measured 87% of more than 10,000 scheduled stop visits in a day across 13 routes.

What it produces

FileContents
leave_times.csvOne row per run, timepoint and day: scheduled leave time, actual leave time, minutes late.
leave_times_by_run.csvOne row per run and timepoint, one column per day holding that day's minutes late.
report.htmlRoute-by-route chart of every departure against its scheduled time, and a table of all departures.

A row of leave_times.csv looks like this:

service_date,route,trip_id,stop_name,scheduled_leave,actual_leave,minutes_late
2026-09-16,BL,WkOBLBL0830,Breiel Blvd at McDonalds,09:15:00,09:12:45,-2.2

A Parquet copy (leave_times.parquet) keeps column types and loads directly into Python, R, DuckDB or a spreadsheet.

How it works

  1. Each GPS position a bus reports is placed at a distance along its route, using the route's path from the schedule. Positions only move forward, so loop routes and routes that double back are handled.
  2. The moment the bus left each timepoint is interpolated between the GPS positions just before and after it. Positions more than two minutes apart are never interpolated; those stops are left blank rather than guessed.
  3. If the feed reports that a bus is stopped at a stop, that report is used first. If GPS shows the bus standing at the stop, arrival and departure are measured separately.
  4. Predicted times from the feed are never used as actual times. Every estimated time records how it was measured and its uncertainty.
  5. Each service day is measured on its own, then the days are stacked side by side. Nothing is averaged.

Scheduled times follow the GTFS rules exactly, so trips after midnight stay on the correct service day and daylight-saving changes are handled correctly.

Running it

It needs Python 3.9 or newer. Install once:

python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
pip install -e .

Then give it a schedule and your realtime files for a date range:

python -m tdp.history --start 2026-09-01 --end 2026-09-30 \
    --gtfs path/to/gtfs.zip --rt path/to/realtime_folder/

Realtime data can be a folder of raw GTFS-Realtime .pb snapshots, flattened Parquet archive files, or your own CSV export with its column names mapped in a small configuration file. Files are read one day at a time, so months of data fit on a laptop.

Limitations

  • Actual times are estimates from GPS reported about every 20 seconds, typically accurate to within 10 to 30 seconds.
  • Missing data is not random. A tracker that was off or a detour off the mapped route leaves departures unmeasured.
  • Canceled trips and skipped stops cannot yet be told apart from missing data.
  • One schedule version is used per run, so compare runs within one schedule period.
