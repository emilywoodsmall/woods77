Transit Schedule Adherence Analyzer

September 2026

Every run of a bus route repeats each day at the same scheduled times. This tool measures when the bus actually left each timepoint on every day, so the same scheduled leave time can be compared against many days of real departures, and runs that are consistently late stand out.

It works with any transit agency that publishes a standard GTFS schedule and GTFS-Realtime vehicle positions. Nothing in the code is specific to one agency. It was first tested on Butler County Regional Transit Authority (Ohio), where it measured 87% of more than 10,000 scheduled stop visits in a day across 13 routes.

Instructions

You need two kinds of data: the agency's schedule (GTFS), which is almost always public and easy to find, and a record of where its buses actually were (GTFS-Realtime Vehicle Positions), which usually has to be collected over time. The steps below cover both, then installing and running the tool.

Step 1. Get the schedule (GTFS)

GTFS is a zip file of text tables (stops.txt, trips.txt, stop_times.txt and others) describing every scheduled trip. Almost every US transit agency publishes one for Google Maps and other apps, so it is very likely available.

  1. Check the agency's website. Look for a page called "Developers", "Open data", "GTFS" or "App developers". The download is usually a link ending in .zip.
  2. Or search a directory. Mobility Database and Transitland list thousands of agencies. Search for the agency name and download its GTFS feed.
  3. Use the schedule version that was in effect for your dates. Agencies publish a new GTFS when service changes (often each season or semester). Open feed_info.txt or calendar.txt inside the zip to see which dates it covers. Transitland keeps older versions if you need a past schedule.

Keep the zip as downloaded. You do not need to unzip it; the tool reads a .zip or a folder.

Step 2. Get realtime vehicle positions (GTFS-Realtime)

GTFS-Realtime is a live feed that reports each bus's GPS position about every 15–30 seconds. The tool needs the Vehicle Positions feed. (A feed that only has "Trip Updates", which are arrival predictions, is not enough.) The live feed only ever shows the current moment and most agencies do not keep its history, so you need one of these:

Option A: Collect it yourself (most reliable).

  1. Find the feed's URL. It is usually listed on the same developer page as the GTFS, or under the agency's entry on Mobility Database or Transitland. Vehicle Positions URLs often contain words like vehiclepositions or VehiclePositions.pb.
  2. Check whether it needs an API key. Some agencies require a free registration and an API key, which is sent with each request. The developer page explains how.
  3. Save a snapshot every 20 seconds. On a Mac or Linux computer, open Terminal and run the following, replacing the URL with the agency's Vehicle Positions URL: 
    mkdir -p realtime
while true; do
  curl -s -o "realtime/vp_$(date -u +%Y-%m-%dT%H-%M-%SZ).pb" \
    "https://example-agency.com/gtfs-rt/vehiclepositions"
  sleep 20
done
    Each snapshot is saved with the time in its file name, which the tool uses. If the feed needs an API key, add it to the curl line as the agency instructs, for example -H "x-api-key: YOUR_KEY". Press Control + C to stop.
  4. Leave it running for as many days as you want to study. On a Mac, run caffeinate -i in a second Terminal window to stop the computer from sleeping. A small agency produces a few thousand small files per day, typically well under 1 GB per month. A Raspberry Pi works well as an always-on collector.

Option B: Download past data from a public archive. Some services record agencies' feeds and publish the history. The tool can download from gtfsrt.io directly: add the agency's Vehicle Positions URL to its configuration file under archive: vehicle_positions_url:, and leave out --rt when running it. Check that your agency is covered and which dates are available before relying on it.

Option C: Ask the agency. Many agencies keep automatic vehicle location (AVL) records from their own systems and can export them as a CSV. The tool reads CSV files once their column names are mapped in the configuration file.

Realtime data must cover the whole service day. In the Americas, evening trips run past midnight UTC, so a service day's data can span two calendar dates of files. Give the tool the whole folder and it sorts every record into its correct day.

Step 3. Install the tool

Download the code (zip) and unzip it. It needs Python 3.9 or newer. Open Terminal in the unzipped folder and run once:

python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
pip install -e .

In a new Terminal window later, run source .venv/bin/activate again from the same folder before using the tool.

Step 4. Run it

Point it at the schedule and the realtime folder, with the range of service dates to measure:

python -m tdp.history --start 2026-09-01 --end 2026-09-30 \
    --gtfs path/to/gtfs.zip --rt path/to/realtime/

It prints one line per day showing how many departures it measured. Files are read one day at a time, so months of data fit on a laptop, and days already processed are reused if you rerun with a longer range.

Step 5. Open the results

Results are written to output/<feed>/history_<start>_to_<end>/. Open report.html in a browser to see every route, or open leave_times.csv in a spreadsheet. The file details/daily_summary.csv shows how much of each day was measured; check it first, since a day with little realtime data tells you little.

What it produces

leave_times.csvOne row per run, timepoint and day: scheduled leave time, actual leave time, minutes late.

A row of leave_times.csv looks like this:

service_date,route,trip_id,stop_name,scheduled_leave,actual_leave,minutes_late
2026-09-16,BL,WkOBLBL0830,Breiel Blvd at McDonalds,09:15:00,09:12:45,-2.2

A Parquet copy (leave_times.parquet) keeps column types and loads directly into Python, R, DuckDB or a spreadsheet.

The commuter routes to Cincinnati ran furthest behind. CincyLink and CincyLink Express were more than 5 minutes late at most timepoints, and their morning trips between 8 and 10 AM left 24 to 41 minutes late. Several consecutive trips were late by similar amounts, which is the pattern of one morning delay carrying through a vehicle's schedule rather than a string of separate problems.

A few timepoints are late on most trips. On the R3, Miami Station D, the Meijer/West Hamilton Park & Ride and Market Street Station (Area B) were typically 5 minutes late, with nearly half of departures more than 5 minutes behind. On the Gold Line, Baltimore St at 14th Ave, First Ave at Clinton St and Yankee Rd at Meadow Ave showed the same pattern. These are the first candidates for schedule adjustments, once more days confirm them.

The Blue Line has the opposite problem. It was rarely late, but a quarter of its departures left timepoints more than a minute early, which means riders arriving on time could miss the bus. That suggests its running times are longer than needed in places.

The Oxford routes (O1–O4) were the most reliable, leaving on time at 85–100% of timepoints. Lateness across the whole system peaked around 8 AM, noon and 4 PM, when about 22% of departures left more than 5 minutes late.

Coverage matters when reading the numbers. The Red Line had no GPS data after about 1:30 PM, so only 58% of its departures could be measured and its afternoon performance is unknown. The data file used ends at 8 PM Eastern, so evening trips are not included. These results describe a single weekday; running the tool over several weeks shows which patterns repeat.

How it works

  1. Each GPS position a bus reports is placed at a distance along its route, using the route's path from the schedule. Positions only move forward, so loop routes and routes that double back are handled.
  2. The moment the bus left each timepoint is interpolated between the GPS positions just before and after it. Positions more than two minutes apart are never interpolated; those stops are left blank rather than guessed.
  3. If the feed reports that a bus is stopped at a stop, that report is used first. If GPS shows the bus standing at the stop, arrival and departure are measured separately.
  4. Predicted times from the feed are never used as actual times. Every estimated time records how it was measured and its uncertainty.
  5. Each service day is measured on its own, then the days are stacked side by side. Nothing is averaged.

Scheduled times follow the GTFS rules exactly, so trips after midnight stay on the correct service day and daylight-saving changes are handled correctly.
